# Pixel Studio — первый каркас

Встроенный модуль форка Godot для 3D pixel art. Это первый этап **в ширину**: общие типы, рабочие заготовки и маршруты редактирования. Это ещё не законченный специализированный движок и не доказанная оптимизация всех систем Godot.

Модуль включается при обычной сборке автоматически. Нужны GDScript, 3D и 3D physics. Скрипт интерфейса встраивается в бинарник на этапе сборки; устанавливать addon в каждый игровой проект не нужно. Игровые классы написаны на C++ и доступны в экспортных шаблонах, собранных с этим модулем.

## Начало работы

1. Запустите `PixelStudio.cmd` в корне репозитория: он открывает демопроект собранным редактором из `bin`. Если бинарника ещё нет, соберите редактор по инструкции ниже; обычный установленный Godot не содержит классов `Pixel*`.
2. Откройте проект `demo/pixel_studio/project.godot` либо свой новый проект.
3. Откройте основную вкладку **Pixel Studio**.
4. Выберите **Сцены**, путь нового файла и **Сохранить новую заготовку и открыть**.
5. Создайте отдельные сцены объектов, манекенов, энтити и UI. Вкладывайте сохранённые сцены в мир через дерево Godot.
6. Редактируйте положение и параметры узлов в 3D / инспекторе. Запустите мир клавишей F6.

В демонстрационном `world.tscn` двор создаётся скриптом при запуске: нажмите F6, чтобы увидеть деревья, колонны и персонажа. Создаваемые через Pixel Studio заготовки содержат обычные редактируемые узлы, видимые до запуска.

Существующие файлы кнопка создания не перезаписывает. Изменения текущей сцены сохраняются обычным Ctrl+S. Добавление деталей, коллизий, креплений, анимаций, изменение цвета и положения используют Undo / Redo Godot.

## Контракты объектов

- `PixelObject3D`: декоративный корень, назначение скрипта запрещено. Детали внутри него также не предназначены для скриптов.
- `PixelEntity3D`: интерактивный корень; скрипт может управлять предметом. Крепления — `PixelAnchor3D`.
- `PixelMannequin3D`: разновидность энтити для персонажа. Скелет — стандартный `Skeleton3D`, крепления — `BoneAttachment3D`.
- `PixelPiece3D`: MeshInstance3D для отдельного многогранника. Отвергает скрипты с `_process` / `_physics_process`, включая унаследованные методы. Пользовательские методы доступны через `call()`.
- `PixelAnchor3D`: Marker3D с таким же событийным контрактом скрипта.

Корень персонажа сам по себе не CharacterBody3D. Физическое движение и контроллер добавляются отдельно: это позволяет не навязывать один способ движения всем NPC. Коллизия из конструктора — статическая коробочная аппроксимация текущей позы, а не автоматически следующий за анимацией hitbox. Для подвижной физики нужны соответствующий PhysicsBody3D и настройка слоёв.

`Object::set_script()` сделан виртуальным также в release-сборках: это позволяет специализированным нодам проверять назначаемый скрипт через общий API. Изменение затрагивает назначение скрипта, а не покадровый цикл.

Ограничения специализированных классов — контракт авторинга, не защита от намеренного обхода через произвольные обычные узлы или изменения движка. Горячая перезагрузка скриптов требует отдельного развития валидатора. «Сплав» скриптов пока не реализован: нужны правила конфликтов имён, состояния и порядка вызовов; конкатенация исходников недостаточна.

## Пиксельный профиль

`PixelWorld3D.resolution` по умолчанию 480 × 270. При запуске он применяет viewport stretch с целочисленным масштабом и сохранением пропорций, отключает MSAA, TAA и screen-space AA. В SubViewport задаётся его внутренний размер; внешний SubViewportContainer должен масштабировать его с nearest filtering. Корневое окно редактора при редактировании не меняется.

`PixelCamera3D` по умолчанию ортографическая, с изометрическим наклоном. Детали используют nearest texture filtering. Шейдерный стенд демонстрирует ступенчатое освещение и цвет; само снижение разрешения выполняется viewport, а не шейдером материала.

Сейчас вместе с миром масштабируется и экранный UI. UI в отдельном высоком разрешении — следующий профиль. Сглаживание движения камеры, shimmer-тесты, фиксированная палитра и стабильность теней ещё не реализованы. Числа FPS и экономии памяти без замеров не заявляются. Проверочная сборка с `optimize=none` предназначена для разработки, не для сравнения производительности.

Системы Canvas / Control сохранены для UI. Штатные 2D / 3D редакторы и обычные классы Godot пока доступны. Строгое ограничение типов проектов и специализированный мастер создания проекта ещё предстоят; сейчас специализация обеспечивается рабочими областями и PixelWorld3D.

## Кат-сцены и камеры

```gdscript
if $Cutscene.start($PlayerCamera):
    # При необходимости запустите AnimationPlayer или игровую последовательность.
    pass

$Cutscene.finish()       # Возвращает камеру и добавляет after_cast_scene.
$Cutscene.finish(false)  # Возвращает камеру без применения последствий.
```

Камера ролика должна находиться в том же Viewport, что и переданная активная камера игрока. Чужой Viewport отклоняется. Если другой сценарий уже переключил камеру, finish не перехватывает её обратно. `after_cast_scene` — PackedScene, добавляемая к родителю кат-сцены только при успешном завершении активного запуска. Повторный finish ничего не создаёт.

`temporary_scene` создаётся при start и ставится в очередь удаления при finish. Заготовка содержит трёхсекундное движение камеры и соединения сигналов для запуска / завершения AnimationPlayer. Временный реквизит редактируется как отдельная PackedScene; постоянные последствия задаются через `after_cast_scene`.

Это локальное управление камерой. Выбор участников сетевой кат-сцены, RPC и синхронизация остаются на уровне игры. Одновременные локальные участники с разными Viewport используют отдельные экземпляры кат-сцены.

## Граф ИИ

`PixelBehaviorGraph.steps` — массив словарей: `action`, `parameters`, `next` и редакторская `position`. Вход — шаг 0, `next = -1` завершает граф. Циклы допустимы: один вызов `advance()` выполняет ровно один шаг и не обходит цикл синхронно. Повторный вызов из обработчика сигнала блокируется. Нет индивидуального `_process()` для каждого мозга.

```gdscript
func _ready():
    $Brain.action_requested.connect(_on_action)

func _on_action(action: StringName, parameters: Dictionary):
    match action:
        &"show_ui":
            $UI.show()
        &"find_path":
            # Здесь игра обращается к NavigationAgent3D.
            pass

func on_decision_event():
    $Brain.advance()
```

`search_object`, `find_path`, `try_hit_player`, `show_ui` в первом каркасе — идентификаторы действий, а не реализованные игровые функции. Пользовательские названия и параметры можно задавать в ресурсе через инспектор. Рабочий граф сначала меняется в редакторском буфере; кнопка **Применить граф** записывает его в выбранный Brain с Undo / Redo. Перед выходом примените граф и сохраните сцену. Локальные изменения буфера пока не восстанавливаются после перезапуска редактора.

## Сборка и проверки

Обычная сборка Godot включает модуль. Для Windows с MinGW, например:

```text
scons platform=windows target=editor use_mingw=yes module_pixel_studio_enabled=yes accesskit=no angle=no d3d12=no tests=yes -j8
```

Для экспортных шаблонов используйте `target=template_debug` и `target=template_release` с включённым модулем. Шаблоны обычного Godot не знают классы Pixel Studio.

На этой машине MinGW из CLion не обрабатывает response-файлы через `gcc-ar`. Для воспроизводимой сборки предусмотрен `tools/build_windows.py`: он может использовать обычные `ar` / `ranlib`, не изменяя установленный компилятор. Например:

```text
python modules/pixel_studio/tools/build_windows.py --mingw-bin "C:\Program Files\JetBrains\CLion 2025.2.3\bin\mingw\bin" --direct-ar platform=windows target=editor use_mingw=yes accesskit=no angle=no d3d12=no vulkan=no opengl3=yes debug_symbols=no optimize=none tests=yes modules_enabled_by_default=no module_gdscript_enabled=yes module_pixel_studio_enabled=yes module_freetype_enabled=yes module_svg_enabled=yes module_godot_physics_3d_enabled=yes module_text_server_fb_enabled=yes module_zip_enabled=yes -j8
```

Этот облегчённый проверочный вариант использует Compatibility renderer и не содержит полного набора импортёров стандартного Godot. Для обычной разработки с импортом моделей собирайте с модулями по умолчанию. Скрипт использует SCons из окружения или локальной `.build_tools`.

Проверки:

```text
bin/godot.windows.editor.x86_64.exe --test --test-case="*PixelStudio*"
python modules/pixel_studio/tests/run_editor_smoke.py bin/godot.windows.editor.x86_64.exe
python modules/pixel_studio/tests/run_editor_smoke.py bin/godot.windows.editor.x86_64.exe --visual
bin/godot.windows.editor.x86_64.exe --headless --path demo/pixel_studio --script ../../modules/pixel_studio/tests/demo_smoke.gd
```

Editor smoke открывает все разделы, проверяет редактирование графа, а в собранном форке — создание и упаковку заготовок, Undo / Redo деталей и костей. Вариант `--visual` дополнительно рисует шейдерный стенд на реальном рендерере и сохраняет снимок редактора в `.pixel_studio_checks/editor-preview.png`. C++-тесты проверяют событийные детали, циклы / завершение ИИ, пиксельный viewport и изоляцию камер двух Viewport. Ручная проверка: создание мира, сохранение / повторное открытие, живое изменение шейдера и F6.

Проверено 17.10.2026 на Windows / MinGW, Compatibility (Intel Iris Xe): сборка редактора, 4 C++-теста / 125 проверок, editor smoke без окна и с реальным рендерингом, запуск демо и снимок 480 × 270. Это проверка работоспособности каркаса, не измерение производительности и не проверка экспортных шаблонов.

Следующий крупный этап: встроить инструменты моделирования непосредственно в 3D viewport, добавить полноценный таймлайн анимаций / кат-сцен и замерить стоимость сцен с сотнями объектов до выбора оптимизаций геометрии.
